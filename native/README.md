# Native desktop capabilities

`core` contains process-local file indexing/search, Unix PTY resources, and narrow credential storage/import capabilities. `binding` is a thin napi-rs adapter that produces one `.node` library. Neither crate owns an engine process, app-server client, session, plugin ledger, window, or shell dispatcher. TypeScript owns those business boundaries and renderer delivery.

## Build and gate

From the repository root, with the Cargo slot available:

```sh
CARGO_BUILD_JOBS=4 cargo check --locked --manifest-path apps/desktop/native/Cargo.toml --workspace --all-targets --all-features
CARGO_BUILD_JOBS=4 cargo clippy --locked --manifest-path apps/desktop/native/Cargo.toml --workspace --all-targets --all-features -- -D warnings
CARGO_BUILD_JOBS=4 cargo test --locked --manifest-path apps/desktop/native/Cargo.toml -p klaus-native-core
node apps/desktop/native/scripts/build.mjs
node apps/desktop/native/scripts/build.mjs --credential-fixtures
npm --prefix apps/desktop run typecheck
npm --prefix apps/desktop run build:main
node apps/desktop/native/scripts/test-electron.mjs
node apps/desktop/native/scripts/test-electron.mjs --credentials
node apps/desktop/native/scripts/test-windows-credentials.mjs
node apps/desktop/native/scripts/test-mcp-credentials.mjs
node apps/desktop/native/scripts/test-ssh.mjs
```

The build script defaults to release, fixes `CARGO_BUILD_JOBS=4`, and emits `artifacts/klaus-native-<platform>-<arch>.node` plus a SHA-256 manifest. The manifest records the Git commit, dirty status, Cargo.lock digest, and native source content digest. The source digest covers sorted relative paths, a NUL delimiter, raw contents, and another NUL for Cargo files, the build script, and Rust source files. A source change during compilation rejects the artifact. `--debug` is available for diagnosis. Each architecture must be built on its target toolchain. Packaging must place the `.node` outside ASAR and supply its absolute path to `loadNativeAddon(path)`; signing/notarization and installer inclusion belong to the release integration.

`--credential-fixtures` uses a separate Cargo target directory and emits only under `artifacts/fixtures/`. Only that compile-time feature exports a memory-keychain factory; the production addon has no fixture backend switch. Credential tests use temporary files, a synthetic SQLite safeStorage row, and memory keychain entries. They do not access the system keychain. The credential Electron test needs Python 3's standard SQLite module to create its temporary input database.

The Electron test runs a normal Electron application, loads the actual library in the main process, and checks the same process ID. It also creates a hidden, sandboxed renderer with context isolation, routes terminal commands, and waits for targeted delivery ACKs. It does not use `ELECTRON_RUN_AS_NODE`. Test results go to ignored `test-results/electron.json`.

## TypeScript entry points

`main/native/binding.ts` defines the narrow ABI. `NativeCapabilities` wraps it with explicit trusted owners. Call `registerOwner(owner)` when the host creates a trusted window/session, `closeOwner(owner, deadlineMs)` when it is destroyed, and `shutdown(deadlineMs)` before quitting. An incoming IPC request must never implicitly register its own owner.

`registerNativeHandlers(registry, options)` registers `engine:workspaceFileSearch` and the four existing terminal channels. The application supplies authorized workspace roots, resolved terminal cwd/executable/environment, and a targeted, bounded `deliver(senderId, channel, payload)` transport. Its returned `attachOwner(senderId)` and `detachOwner(senderId)` follow the WebContents lifecycle. Engine/session/provider access checks remain in the supplied resolvers.

The `deliver` promise must resolve after consumption/ACK or reject on a bounded timeout. Resolving immediately after an unlimited `webContents.send` queue would remove end-to-end pressure. Existing renderer payloads retain `id/data` and `id/exitCode/signal`; `resourceId` and `sequence` are additive diagnostic fields. IPC ACKs need their own delivery ID because UTF-8 EOF can produce a tail data delivery and an exit delivery from one native event.

## IDs, queues and lifecycle

- A search has an explicit `operationId`. Admission happens synchronously before its worker is queued. Cancellation and deadline checks cover directory walking, git stdout, scoring, and the final result. Completed and cancelled operations leave no tombstones. At most eight searches are owned at once.
- The one-shot file index is a fresh snapshot on each call, preserving root ignore rules, git-listed files, ancestor directory entries, basename ranking, Unicode folding, lexical ties, zero limits, and negative slice limits. It has no watcher cache. Walking stops at 200,000 entries or 32 MiB of path data; truncation is explicit and the renderer handler rejects it instead of silently returning a partial listing. Missing roots return an empty result; non-UTF-8 paths and invalid arguments are explicit errors.
- A persistent search session walks its roots once at creation and then re-ranks that snapshot per query, so a picker querying on every keystroke pays one walk instead of one per keystroke. The snapshot is frozen for the session's lifetime and nothing watches the filesystem: a file created after the session opened is not offered until it is reopened. This is the deliberate counterpart to the one-shot path above, whose freshness a session gives up to avoid a repeated walk. Creation rejects a truncated snapshot rather than serving a partial one, validates the root list and identifier before admission, and refuses more than four live sessions — each pins a whole tree snapshot, so that cap bounds memory rather than descriptors. Queries take their own deadline at query time, not at creation, may run up to four deep per session, and check cancellation between paths. A session merges multiple roots in workspace order and tags each hit with the origin root so the host keeps prefixing a secondary root's path exactly as the one-shot handler does. Stopping cancels in-flight queries and seals the session; shutdown stops and deregisters every session and reports any query that outlived its deadline by operation id.
- A session has no event queue: results are returned from the query call. A push channel only earns its keep when results arrive in increments a consumer must stream, and a snapshot rank produces one complete result per query, so an event pump here would be a queue with a single possible message. Cancellation still works through the per-query `operationId`.
- A PTY has a fresh `resourceId` for every generation, independent of its UI terminal ID. Events carry contiguous `sequence` values, raw data bytes, and a final exit status. TypeScript decodes UTF-8 across chunk boundaries only at the renderer boundary.
- Each PTY has one worker thread. Native reads/writes are nonblocking on Unix. Output has 64 data slots of at most 16 KiB, one pending read, and one reserved exit slot. A full queue stops further reads and pressures the child; it never silently drops terminal bytes. Input has eight pending operations of at most 64 KiB each; overflow fails with `BACKPRESSURE`.
- Write and resize requests have explicit operation IDs and completion receipts. A partial or cancelled write reports its accepted prefix as `bytesWritten`; callers must not blindly retry the entire payload. The UI handler serializes pastes and caps each at 1 MiB.
- There is one async event consumer per PTY. No threadsafe-function callback queue or native callback can outlive the TypeScript event pump. `close()` shares a promise and fences further sink invocations before it resolves. An already invoked asynchronous sink can still finish its own work; a stalled/rejected sink makes `deliveryComplete` false.
- Closing first requests termination, escalates an owned child/terminal process group, and drains ordered data before exit. At the deadline, unread output is reported as incomplete and all master handles are closed so a blocked slave can finish. Known discarded bytes, the final emitted sequence, queue peak, and an error are returned. Bytes still in the kernel cannot be counted exactly; `outputComplete=false` explicitly covers them.
- Shutdown permanently seals admission and cancels searches/session queries/PTY operations, deregistering every search session. Its deadline reports unfinished operations/resources instead of claiming success, naming a session query that outlived its deadline by operation id. Completed resources are released after delivery; there is no global retired-resource registry. A blocked filesystem syscall or process creation cannot be forcibly cancelled safely in-process and may remain in the returned pending list.

Before removing a managed directory, the main process calls the handler runtime's `quiesceDirectory(absoluteRoot, deadlineMs = 5000)`. It closes matching terminals, includes pending cwd resolution, recognizes canonical paths and descendants, and keeps new terminal admission blocked until the returned idempotent release function is called in the deletion's `finally`. Overlapping leases are independent. A failed lease releases its own admission block and rejects; the caller must not delete the directory. A terminal whose event pump ended while its native worker is still closing remains tracked. Incomplete close results fail the current deletion attempt; a later attempt can proceed after physical termination and delivery have settled.

## Credentials

`NativeSubscriptionCredentials({configRoot, userHome, addon?})` implements the main-process subscription credential dependency. It exposes `readClaudeOAuth`, `writeClaudeOAuth`, `removeClaudeOAuth`, `readLocalClaudeCredential`, and `readQoderIdeCredential`. Reads distinguish absence from a backend error. The Qoder result is already projected to the engine's `userInfo` shape; HTTP/OAuth, account state, and `qoder/adoptCredential` remain TypeScript service responsibilities. No renderer IPC exposes these raw primitives.

The native class takes a resource ID; each operation has its own ID, and responses carry both IDs. Admission and enqueue are synchronous, preserving write/logout order. One dedicated worker executes at most eight outstanding operations, with a process limit of four credential workers. Promise waiting uses Tokio rather than a blocking libuv job. Queued work can be cancelled before it starts. An OS operation already in progress cannot be rolled back on deadline: its waiter reports `credential_operation_outcome_unknown`, and callers must not retry a mutation blindly.

Call `close(deadlineMs)` after the account/subscription service has stopped its work. Close seals admission, cancels queued commands, fences late credential results, and shares a promise. Its report contains `complete` and `pendingOperations`; an OS keychain prompt or blocked filesystem call can remain in progress after the deadline. Treat an incomplete report as unfinished shutdown. There are no native event callbacks in this API.

On macOS, Security.framework reads and writes the existing Claude service/account identity, suffix, and conditional config-root hash. It accepts existing JSON, trailing-NUL JSON, and legacy hexadecimal representations. New writes use Keychain only; denial is explicit. A successful write removes only OAuth keys from an existing plaintext compatibility copy and reports a warning if that cleanup fails. Logout attempts both existing stores and preserves other record keys such as plugin secrets. Linux retains its existing 0600 file backend. Windows subscription writes use the separately injected Electron capability described below; the Rust class alone preserves an existing DPAPI-backed blob and reports `windows_dpapi_credentials_not_migrated` instead of overwriting it.

Local Claude import reads `~/.claude/.credentials.json` first, then the existing service-only macOS Keychain record. Qoder import opens the IDE database read-only with WAL visibility, strictly validates buffer bytes, decrypts the existing macOS OSCrypt format, and does not mutate the IDE. Qoder safeStorage on Windows/Linux remains explicitly unsupported. Generic MCP/plugin/engine credential keys are outside this subscription slice.

### Windows safeStorage and the P5 key dependency

On Windows, construct the adapter after app readiness with `windowsSafeStorage: safeStorage`, using Electron 44's original object or bound methods. The required interface is `isAsyncEncryptionAvailable(): Promise<boolean>`, `encryptStringAsync(string): Promise<Buffer>`, and `decryptStringAsync(Buffer): Promise<{result: string; shouldReEncrypt: boolean}>`. This is Electron's existing in-process native implementation. `WindowsCredentialStore` supplies one bounded, serial file transaction queue per adapter; the application must own one adapter per config root. It uses asynchronous filesystem I/O, at most eight pending operations, immutable snapshots of queued writes, atomic encrypted-file replacement, explicit operation/deadline/close outcomes, and no new plaintext fallback. Close joins the Windows transaction worker and the addon resource under one deadline.

An existing `.credentials.enc` is not necessarily a raw DPAPI payload. The historical writer called `safeStorage.encryptString`. Electron 33's Windows OSCrypt format is `v10`, a 12-byte nonce, and AES-256-GCM ciphertext/tag. Its AES key is stored under `os_crypt.encrypted_key` in the originating Electron profile's `Local State`: Base64-encoded `DPAPI` prefix plus the DPAPI-protected key. The optional `os_crypt.audit_enabled` field accompanies it. The new application's `configRoot/electron/Local State` must not initialize a different key before P5 handles this dependency.

P5 owns the following startup preparation, before `app.whenReady()` or any Chromium/safeStorage initialization:

- Back up the existing credential blob and the originating `Local State` together. Candidate profiles are the existing packaged profile (commonly `%APPDATA%/Klaus`) and the historical development profile: `KLAUS_USER_DATA_DIR` when specified, otherwise `%APPDATA%/klaus-desktop-dev`. The development path is pinned by `git show pre-electron-removal:apps/electron/src/main/index.ts`, `configureDevUserData`; the retired client is consulted only for the persisted path/format.
- Select the known originating profile. If the new `Local State` has no encryption key, merge only `os_crypt.encrypted_key` and, when present, `os_crypt.audit_enabled`, preserving all unrelated fields. Keep the old file and backup intact. Do not copy an entire browser profile or cookies as part of this credential operation.
- For an encrypted-only record, a missing required key yields `windows_credentials_legacy_key_required`. Different existing keys or ambiguous old profiles yield `windows_credentials_key_conflict`; do not choose or replace a key by guessing. Inject the corresponding `windowsKeyError` so reads return an explicit error and writes cannot overwrite the old blob. A decryption failure with a selected key is `windows_credentials_decryption_failed`, never a successful signed-out result.

The current Windows plaintext backend can leave a valid `.credentials.json` beside the historical `.credentials.enc`. `prepareWindowsProfile({configRoot, appData, legacyUserDataDir?})` owns synchronous startup preparation before Chromium readiness. It backs up the raw JSON, encrypted bytes, and available Local State files, and pins the backup manifest and both credential hashes. It preserves a valid current `claudeAiOauth`, or compatible `tokens`, even if a v1 profile-ownership marker already exists. It returns `legacyPlaintextProof` and `legacyMigrationJournal`; after readiness, inject these as `windowsLegacyPlaintextProof` and `windowsLegacyMigrationJournal` alongside `windowsSafeStorage: safeStorage` and `windowsKeyError`.

The adapter verifies the raw-byte hashes again before reading the compatibility record and immediately before replacing encrypted data. A decryptable old encrypted record contributes unrelated keys; the current plaintext record takes precedence. If the old blob cannot be decrypted, its verified backup protects the unknown keys and only the proven current record is migrated. A missing legacy key does not hide that proven login; a conflicting key still blocks writes. Current encryption must be available, and a new write must produce encrypted output. No new plaintext fallback is introduced.

The asynchronous journal has two callbacks: `prepare(newEncryptedSha256)` persists a v2 pending marker before encrypted-file replacement, and `commit(newEncryptedSha256)` marks the new profile as owner after replacement and before plaintext cleanup. The pending marker contains `legacyProof`, `backupDirectory`, `backupManifestSha256`, optional `keyDigest`, and `pendingNewEncryptedSha256`. The callbacks verify the backups, current profile key, credential hashes, and unchanged marker; they never modify Local State. A first profile key can reach disk after async encryption finishes, so preparation waits asynchronously for at most 15 seconds and revalidates the originals afterward; the adapter's overall operation deadline still applies. An unresolved ownership commit blocks later credential mutations so another write cannot invalidate the recovery hash. Logout keeps an encrypted empty record before cleanup when no unrelated keys remain. Once an encrypted record has become authoritative, an unexpectedly missing file is explicit rather than a reason to read an old plaintext login.

On restart, the original encrypted hash resumes the old proof; the intended new hash selects the new encrypted record and finishes ownership. A third hash is an explicit error. An owned v2 marker never restores plaintext priority. A leftover `legacyPlaintextCleanupSha256` permits removal of only the exact backed-up OAuth copy. If cleanup fails or the plaintext hash changes, startup returns a warning and `legacyPlaintextCleanupSha256`; inject it as `windowsLegacyPlaintextCleanupSha256` so later normal writes also preserve that unverified file. `pruneLegacyClaudeOAuth(bytes)` and `readLegacyClaudeOAuth(bytes)` are pure helpers shared by startup and the adapter; the only removed keys are `claudeAiOauth` and `tokens`.

The application must hold its profile/workspace ownership lock and create one preparation result and one credential adapter per config root. Hash checks reject observed external changes; they do not provide a filesystem compare-and-swap against an unrelated process that ignores that ownership. The dedicated Windows gate `node apps/desktop/native/scripts/test-windows-profile.mjs` creates disposable profiles and injects process exits before and after replacement, then starts a new Electron process to test recovery with the actual OS crypto backend.

Format sources: [Electron 33 safeStorage](https://raw.githubusercontent.com/electron/electron/v33.4.11/shell/browser/api/electron_api_safe_storage.cc), [Chromium Windows OSCrypt](https://raw.githubusercontent.com/chromium/chromium/130.0.6723.137/components/os_crypt/sync/os_crypt_win.cc), and [Electron 44 asynchronous safeStorage](https://raw.githubusercontent.com/electron/electron/v44.2.0/shell/browser/api/electron_api_safe_storage.cc). The Windows gate uses synthetic tokens in a disposable profile and starts a second Electron process to prove the encrypted record survives a process restart. On another platform it explicitly runs only transaction fixtures; it does not claim a Windows OS gate.

## MCP OAuth records

The same `NativeSubscriptionCredentials` instance also implements `readMcpOAuthRecord(serverKey, part)`, `writeMcpOAuthRecord(serverKey, part, value)` and `removeMcpOAuthRecord(serverKey, part)`. `part` is exactly `discovery`, `client` or `tokens`; records are JSON objects. The service computes `serverKey` as `<name>|<first 16 lowercase hex characters of SHA256(JSON.stringify({type,url,headers}))>` with that field order. Discovery, DCR, PKCE, loopback listeners, token refresh and business ownership stay in TypeScript services. These methods are never registered as renderer credential channels.

On macOS, the existing Keychain service remains `agent-engine` and the account remains `mcp:oauth:<serverKey>:<part>`, without a config-directory hash. Security.framework work uses the existing bounded native credential worker. Missing slots return `value: null`; denied, malformed or unavailable secure records return an error and are never treated as a missing login. Windows uses the injected after-ready async `safeStorage` capability and a separate `.mcp-credentials.enc`, preserving the other slots on each atomic replacement. This file is separate from Claude's `.credentials.enc` and the engine's `credentials.enc`; the adapter does not change Local State. A working secure backend is mandatory. Linux currently reports an explicit unsupported capability instead of adding another plaintext fallback.

An old `.mcp-credentials.json` is a map from full account keys to JSON **strings**. The transaction layer migrates a selected record only after the secure backend can be read. It writes an exact 0600 backup named `.mcp-credentials.backup-<raw SHA256>.json` before any legacy cleanup; unrelated records remain intact. `.mcp-credential-migrations.json` stores only ownership hashes and one pending operation, including the before/after legacy file hashes. It contains no token values. A write interrupted before its secure commit leaves the legacy record usable. A secure record found after an interrupted write becomes authoritative. A durable delete intent is idempotently completed, and an owned slot cannot revive an old plaintext token. Cleanup recognizes both its original input and its already-completed output and refuses an observed third hash. If cleanup fails after a secure write, the write reports success with a warning and keeps the recoverable journal; a later blocked recovery reports an explicit error.

Only one transaction owner per normalized config root may be live in this process. It synchronously admits at most eight operations, snapshots queued values and preserves write/delete order. Close seals admission, fences late results and reports unfinished native/crypto/filesystem work. Stop the MCP runtime/OAuth services first so their cancellation rollback can finish, then close this shared credential adapter. The application must also hold its profile ownership lock: hash checks detect observed external changes but cannot provide atomic compare-and-swap against a separate legacy process that ignores ownership.

The MCP Electron gate uses a separately compiled memory-keychain fixture and isolated files to cover native envelopes, order, secure-store failure, exact backups, interruption recovery and bounded shutdown. On Windows it additionally uses actual async safeStorage and reopens the encrypted record in a fresh Electron process. No macOS system credential is read or changed by the gate.

## Platform boundary

Windows PTY uses ConPTY through the same N-API surface and the same resource/event contract. Its process starts suspended, joins a private Job Object, and resumes only after ownership is established. Closing terminates that job and waits for both the root process and all job members. An independent control worker owns the pseudoconsole handle and serializes resize/close; the I/O coordinator uses overlapped named pipes with one fixed buffer per direction. The pipes permit the owner and LocalSystem, reject remote clients, and do not inherit the parent's redirected standard handles.

Normal output remains bounded by 64 queued chunks, one pending read and one reserved exit event. A shutdown deadline reports incomplete output and continues draining into the fixed scratch buffer, with discarded bytes counted explicitly. Windows 11 23H2 can leave `ClosePseudoConsole` blocked if a full output pipe is simply closed; draining must continue until the control worker returns. The TS close barrier prevents further sink calls after its promise resolves. A write cancelled during overlapped I/O reports its known accepted prefix plus `writeOutcomeUnknown`; a control call already submitted when its waiter expires reports `controlOutcomeUnknown`. Do not blindly retry either operation.

The Windows Rust gate includes an ignored child-only fixture entry that the integration tests explicitly execute in owned subprocesses. It exercises Unicode input, resize, ordered exit, three MiB of printable output, output/control pressure, cancellation, failed spawn, and descendant reaping without killing an unrelated child. The normal Electron gate selects the Windows suite automatically, including a sandboxed renderer with acknowledged terminal events. It supplies an explicit Node executable only for the disposable child fixtures. The actual app's terminal executable and environment remain the main process's decision.

Sources: [Microsoft's pseudoconsole lifecycle](https://learn.microsoft.com/en-us/windows/console/creating-a-pseudoconsole-session), [redirected standard-handle behavior](https://github.com/microsoft/terminal/discussions/15814), and [named-pipe access control](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights). Installer signing, clean-machine packaging, Linux/other architectures and remaining platform capabilities require their own gates; native capability slices alone do not complete migration phase P2.

## SSH transport

`NativeSsh` owns one same-process russh connection and one dedicated Tokio thread. Its constructor accepts a fresh resource ID and `{userHome, localUser, agentPath}` from trusted main-process state. Methods are `listHosts(operationId, deadlineMs)`, `connect(operationId, targetJson, deadlineMs)`, `execute(operationId, command, deadlineMs)`, `cancel(operationId)`, `readEvent()`, `answer(operationId, requestId, answerOrNull)`, `report()` and `shutdown(deadlineMs)`. All responses include `resourceId` and `operationId`. This library does not launch a system SSH process, manage engines, construct application workspace URLs or dispatch shell IPC.

Each resource admits at most eight operations; a process admits at most twelve resources. Operations enter synchronously in call order and wait through Promises. Configuration/key files, Include expansion, agent frames, authentication attempts, prompts and command output have explicit bounds. Exec stdout and stderr share a 2 MiB cap, retain original bytes and expose terminal exit status. Exceeding the cap is an error, never truncated success. Cancellation or timeout after sending exec reports `SSH_OPERATION_OUTCOME_UNKNOWN`; the connection is discarded and the command is never replayed. A disconnected remote process may still run, so this outcome must not be presented as a remote rollback.

There is one outstanding challenge and one event reader per resource. Events are `{resourceId, operationId, requestId, sequence, prompt, echo}`; sequence starts at one and increments on delivery. A cancelled undelivered challenge does not create a sequence gap. Answers must match the delivered operation/request pair; null cancels the entire authentication ladder. The TypeScript transport awaits one bounded delivery/ACK at a time. Close seals admission, cancels work, shuts down the owned TCP socket and stops the runtime before reporting `complete: true`. An OS file read or name-resolution operation can outlive its deadline; `complete: false` retains that fact. The wrapper fences new sink invocations immediately, waits for its event pump and reports incomplete shutdown if the pump has not settled. An already invoked asynchronous sink may still finish its own work.

`registerSshHandlers` supplies only `ssh:list-hosts`, `ssh:test`, `ssh:list-dirs`, `ssh:make-workdir`, and `ssh:askpass-answer`. Main must register trusted window owners and call `detachOwner`/`shutdown`; incoming requests cannot register themselves. The handler owns a pool of at most ten connections, keyed by caller and target. Different windows cannot answer each other's prompts. Its `deliver(senderId, 'ssh:askpass', payload)` must resolve after bounded renderer receipt/ACK. Supply the user's home/name and an explicit agent socket snapshot; Windows OpenSSH uses `\\.\pipe\openssh-ssh-agent`, while Unix normally uses `SSH_AUTH_SOCK`. An absent agent path disables agent probing.

Configuration resolution supports Host alternatives/negations, sorted recursive Include with cycle and size checks, first-value precedence, additive IdentityFile, IdentitiesOnly, BatchMode, IdentityAgent, UserKnownHostsFile, and StrictHostKeyChecking `yes`/`accept-new`. Unknown host keys use the existing accept-new policy by default; known, changed and revoked keys are distinguished. New keys must persist under an exclusive file lock before authentication. Authentication tries agent identities, private keys (including passphrases), keyboard interaction and passwords as offered by the server. Active ProxyJump/ProxyCommand, Match blocks, host certificates and unsupported key/path policies fail explicitly. System-wide SSH configuration, GSSAPI, Pageant and certificate authentication are outside this slice. Remote home/directory browsing requires a POSIX shell and UTF-8 paths; directory framing preserves whitespace/newlines and refuses malformed data.

The SSH gate builds a separate loopback fixture binary, then loads the production addon in normal Electron with isolated profiles and sandboxed renderers. The fixture feature is absent from the production binding; this test binary is not a packaged helper. `test-ssh.mjs --fixture-bin=/absolute/path` uses an already built fixture when Cargo must remain idle. Rust tests exercise private keys, passphrases, keyboard challenges, host-key persistence, queue cancellation, stalled handshakes, output limits and command outcome uncertainty. The Electron gate covers native loading, Promise/event identity, actual renderer prompt/answer delivery, caller ownership and shutdown. Remote engine/session integration and installer validation remain separate work.
